# Veil Arena v0.4.0 — ソース版

他のVeilの変更を繰り返し試験するためのVM・仮想ネットワーク基盤です。
1 VMを標準とする範囲を維持し、Mac ARM64/TCGとLinux x86_64/KVMの追加受け入れ結果をまとめました。

## v0.3.0からの変更

- **2 VM lifecycle入口を追加**。2 Node Ready後・Pod適用前でserver runnerを停止し、中断→新規正常クラスタ→watchdog→新規正常クラスタを実行します。4クラスタで既存600秒を共有し、両VMの証拠保存・同期・所有QEMU回収を確認。回収失敗を想定故障の成功に置き換えず、非対応guestは起動前に拒否します。
- **Mac/Linuxの追加検証を記録**。固定入力のF2→F3統合で、ノード間Pod・Service DNS・TCP/UDP・限定NetworkPolicyと解除後復帰、固定Keeperの限定exec拒否・解除後復帰を確認。LinuxとMacでserver側checkpoint故障・復帰も成功しました。
- **Wardenの隔離VM試験入口を追加**。固定CLI/BPFでobserve/enforce、IPv4/IPv6 TCPの限定拒否と対照、ルール解除・SIGTERM/SIGKILL後の通信復帰、証拠同期・QEMU回収を検証します。実証範囲はMac ARM64/TCGの隔離VMで、最新Wardenや物理NICの認定ではありません。
- **Warden非ロード同定を別入口へ分離**。固定systemdサービスのrunning/stopped、不正・保護対象入力を確認します。診断対象プロセス群のBPF syscallなしを確認した試験であり、BPF attachや保護成立の証明ではありません。
- README・完成計画・再実行手順を更新し、過去の資源不足と後続成功を区別しました。既存guest・依存cacheを再利用し、試験ごとの書込みdiskと証拠を分離します。

## 検証結果と読み方

- [Linux x86_64/KVM](../HP_UBUNTU_VALIDATION.md)：固定F2→F3統合の新規6 VM、[2 VM lifecycle](../F2_LIFECYCLE.md)の新規8 VMで成功。
- [Mac ARM64/TCG](../MAC_TWO_VM_VALIDATION.md)：現行main `2ce0bc8` で統合6 VM＋lifecycle8 VMが成功。14のboot IDが異なり、全所有PID不在、QEMU終了0・回収・同期成功、強制回収なし、入力seal・host link/IPv4 route不変を独立確認。watchdogはcheckpoint観測後2117 ms。
- [Warden policyのmain検証](../WARDEN_MAIN_VALIDATION.md)と[非ロード検証](../WARDEN_NONLOADING_VALIDATION.md)は、それぞれの固定入力・ソースでの別記録です。
- 版上げ後のローカルチェック・パッケージビルド・GitHub CIは実VM証拠と別に確認します。[公開確認手順](../V0_4_0_READINESS.md)を参照してください。

過去のruntime証拠を、版番号変更後の全guest再ビルド・再起動や、全ホスト・全製品の成功へ読み替えません。
古いimmutable runner/guestは自動更新されません。再利用時はUID・CPU系統・入力hash・対象ソースを照合してください。

## 使い始める

[1 VM K3s](../F1_K3S.md)、[2 VM通信](../F2_K3S.md)、[F2→F3統合](../F4_ACCEPTANCE.md)、[2 VM lifecycle](../F2_LIFECYCLE.md)、[Warden policy](../WARDEN_POLICY.md)、[Warden非ロード](../WARDEN_NONLOADING.md)から目的の入口を選びます。
Blackholeの[オフライン入口](../BLACKHOLE_WORKFLOW.md)と既存netns一括試験も維持しています。
初回のguest/runner準備と試験を分け、各試験は新規出力先へ実行してください。常設クラスタを提供する入口ではありません。

## 配布と制約

- **ソース版のみ**。VMイメージ・依存バイナリ・生disk・ログ・PCAP・token・kubeconfigは同梱せず、手動バイナリassetも追加しません。Rust・スクリプト・文書はMIT、参照eBPF CはGPL-2.0-onlyです。
- 2 VMはserver4 CPU/16 GiB＋agent2 CPU/4 GiB、各disk32 GiB。同時起動は最大2 VM。起動前に6論理CPU・利用可能RAM24 GiB以上を要求します。これは固定資源契約で、最低必要量の測定ではありません。disk空きは入口ごとの条件に従います。
- agent側停止注入、panic/電源断、過去Linux netns期限超過の根本原因は未検証/未確定として保持します。今回のK3s成功を旧netns問題の解消とは扱いません。
- Keeperの全機能・Pod配備・独自BPF LSM、本番保護、Wardenの実サービス配備・物理NICは認定していません。
- 物理環境・第三者試用・別CNI・IPv6クラスタ・HA・Mac HVFは対象外です。未知の攻撃への防御や性能は保証しません。

今回の到達点で区切り、他のVeilの実開発を優先します。具体的な試験要求や不具合に応じてArenaを保守します。
